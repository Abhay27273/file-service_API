Category 1: Memory & Performance
Q1: Why did you use shutil.copyfileobj instead of simply doing file.write(await file.read())? Answer: Using file.read() loads the entire file into RAM at once. If a user uploads a 2GB video and the server has 4GB of RAM, two concurrent uploads would cause an Out of Memory (OOM) crash. shutil.copyfileobj uses Buffered I/O (Streaming). It reads the file in small chunks (e.g., 64KB), writes that chunk to the disk, and clears it from memory before reading the next one. This keeps memory usage O(1) (constant) regardless of the file size.
Q2: If 1,000 users upload files simultaneously, is your service CPU-bound or I/O-bound? How does this affect your choice of Python/FastAPI? Answer: This service is I/O-bound because it spends most of its time waiting for the Disk (writing files) and Network (receiving bytes), not doing complex math (CPU). Python is excellent for this because while the file is writing to disk, the Global Interpreter Lock (GIL) is released (in standard I/O) or the Event Loop (in FastAPI/Async) yields control. This allows the server to handle other incoming requests while waiting for the disk write to finish, maximizing throughput.

🛡️ Category 2: Security
Q3: You read the first 10 bytes to check for "Magic Bytes." What critical step must you take immediately after that, and why? Answer: I must call await file.seek(0). Reading the first 10 bytes moves the file cursor (pointer) forward to the 10th byte. If I save the file immediately after validation, the saved file will be missing its header (the first 10 bytes) and will be corrupted. seek(0) "rewinds" the cursor back to the start so the full file is saved.
Q4: Why do we check Magic Bytes instead of just validating the file extension (e.g., .png)? Answer: File extensions are meaningless labels that can be easily spoofed. A malicious user can rename a dangerous script (exploit.sh or virus.exe) to cute_cat.png. If we only check the extension, we might accept malware. Magic Bytes are the actual hexadecimal signature at the beginning of the file (e.g., 89 50 4E 47 for PNG) that truthfully declare the file format.
Q5: Why do we generate a UUID (uuid.uuid4()) for the filename instead of using the user's original filename? Answer: Two main reasons:
Security (Directory Traversal): A hacker might upload a file named ../../etc/passwd to try and overwrite system files. Generating our own name neutralizes this.
Collisions: If two users upload profile.jpg, one would overwrite the other. UUIDs guarantee uniqueness.


💾 Category 3: Database & Storage
Q6: Why did you store the file metadata in a database and the file content on the disk? Why not store the binary data (BLOB) directly in the database? Answer: Storing BLOBs in a database (like PostgreSQL/MySQL) is generally a bad practice for large files because:
Performance: Reading large blobs ties up database connections and memory, slowing down simple queries for everyone else.
Cost: Database storage (provisioned SSDs) is much more expensive than Object Storage (S3) or standard disk.
Backups: Database backups become massive and slow to restore. It is much more efficient to store the reference (path) in the DB and the heavy data on a specialized file system.
Q7: In our current code, what happens if the os.remove(path) succeeds but the database delete fails? How would you fix this in production? Answer: This creates a Data Consistency issue.
Scenario: File is gone from disk, but DB says it exists. User tries to download -> 404 Error.
Fix: In a real system, I would use Database Transactions. I would delete the DB record first within a transaction. If that succeeds, I delete the file from the disk. If the file deletion fails, I might roll back the transaction (though re-uploading is rare) or, better yet, use a "Garbage Collector" background job that scans for files in the DB that don't exist on disk (and vice versa) to clean them up eventually.

🌐 Category 4: Architecture & Scalability
Q8: This code saves files to uploads/ on the local server. Why will this fail if we deploy this API to AWS using Docker containers (e.g., Kubernetes or ECS)? Answer: Docker containers are ephemeral (temporary). If the container restarts or crashes, the local uploads/ folder is wiped out, and all user data is lost. Furthermore, in a distributed system with multiple server instances (e.g., Server A and Server B), if a user uploads to Server A, the file exists only on A. If their next request hits Server B, Server B won't find the file. Solution: We must replace local disk storage with a shared Object Store like AWS S3 or Google Cloud Storage.
Q9: What is "Multipart/Form-Data" and why is it required for this API endpoint? Answer: Standard JSON requests (application/json) are not designed to handle binary data efficiently (you'd have to Base64 encode it, increasing size by 33%). Multipart/Form-Data breaks the request into distinct parts. One part can be JSON metadata, and another part can be the raw binary stream of the file. It allows the browser to stream the file bytes directly without expensive encoding overhead.
Q10: The GET /download endpoint returns a FileResponse. What specific HTTP header does it set to ensure the browser displays the image instead of downloading it? Answer: It sets the Content-Type header (also known as MIME type).
If Content-Type: image/png, the browser knows to render the pixels.
If Content-Type: application/octet-stream (or if the header is missing), the browser defaults to downloading the file because it doesn't know what else to do with the bytes.
